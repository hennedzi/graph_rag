## Цель
Каждое событие run получает `duration_ms`, а в конце run пишется сводка (шаги LLM, вызовы инструментов,
p50/p95 по типам, время до первого токена). Без этого невозможно ни доказать ускорение в C2–C5, ни
провести эксперимент D1.

## Контекст: где это в коде
- `harness.py` — цикл агента: здесь происходят вызовы LLM и инструментов (`search_passages`,
  `neighbors`, `find_paths`, `rank_by_ppr`), здесь же события уже получают `seq`.
- `api.py` — запуск run (`POST /runs`), журнал `events`, `run_id`.
- `runs/` — сохранённые трассы; сюда должна лечь сводка.
- `web/src` — страница Harness: строка статуса run.

## Что сделать
1. В `harness.py` оберни каждое место «перед вызовом» / «после вызова» в таймер: `t0 = time.perf_counter()`
   перед вызовом LLM или инструмента, после — `duration_ms = (time.perf_counter() - t0) * 1000`.
2. Добавь `duration_ms` в словарь события перед записью в журнал. Схему событий (`run_id`, `seq`, `type`)
   не меняй — только новое поле.
3. В конце run собери сводку: количество шагов LLM, количество вызовов по типу инструмента,
   `p50_ms` и `p95_ms` по типам, `time_to_first_event_ms`. Сохрани в `runs/` рядом с events.
4. В `web/src` выведи в строке статуса run: шаги, общее время, p95 самого медленного типа.
5. Добавь тест в `test_core.py`: у каждого события в трассе есть `duration_ms >= 0`.

## Границы задачи
- Не меняй порядок и формат существующих полей события.
- Не внедряй SSE и параллелизм — это C1 и C2.
- Не трогай `eval.py`.

## Как проверить

```
cd web && npm run build
```
